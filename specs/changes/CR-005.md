# CR-005: เจ้าหน้าที่เห็นลำดับคำขอที่ค้างอยู่บนหน้ารายละเอียดอุปกรณ์ของ 001 (ปิด Q-SH-05)
ขอโดย: 001 (พรรณธร จันทร์สายทอง @Pannathorn05) หลังทีมปิด Q-SH-05 | วันที่: 2569-11-11 | สถานะ: ตัดสินแล้ว (รับทั้งหมด 2569-11-12)
spec ที่เกี่ยวข้อง: specs/001-equipment-status/spec.md (Draft v4.4 -> Draft v5 เมื่ออนุมัติ)
แก้ไขต่อจาก: CR-004

## ขออะไร และทำไม

| # | เดิม | หลัง CR นี้ | ที่มา |
|---|---|---|---|
| 1 | spec 001 ไม่มี FR เรื่องลำดับคำขอ Q-SH-05 เขียนไว้ว่า "ถ้าคำตอบคือหน้ารายละเอียดของ 001 ต้องเพิ่ม FR ผ่าน CR" | เพิ่ม **FR-EQS-11** และ **AC-EQS-17** (เลขต่อท้าย ไม่เปลี่ยน ID เดิม) | Q-SH-05 ปิดแล้ว 2569-11-11 (ทีมตัดสิน), FR-BRQ-05 (ก) ของ 002, CR-003 |

ข้อความที่เสนอ (เพิ่มเมื่อทีมอนุมัติเลขและข้อความแล้ว):

```
- FR-EQS-11 ที่หน้ารายละเอียดอุปกรณ์รายชิ้น ระบบต้องแสดงคำขอยืมที่ค้างอยู่ของอุปกรณ์ชิ้นนั้นให้เจ้าหน้าที่เห็น
  เรียงตามลำดับที่ส่ง พร้อมลำดับที่ เวลาที่ส่ง (วันที่และเวลา) และชื่อผู้ขอ
  ชื่อผู้ขอคือชื่อที่ผู้ขอพิมพ์เองในฟอร์มคำขอ (FR-BRQ-03 ก ของ 002) ระบบไม่ได้ตรวจกับระบบยืนยันตัวตน
  นักศึกษาไม่เห็นส่วนนี้ (DOM-PRIV-01)                         <- DOM-REQ-01, Q-SH-05, FR-BRQ-05 (ก), CR-005

- [ ] AC-EQS-17 (FR-EQS-11, DOM-REQ-01, DOM-PRIV-01)
      Given อุปกรณ์ชิ้นหนึ่งสถานะ "ว่าง" มีคำขอค้างอยู่ 2 รายการ ผู้ขอ A ส่งก่อน ผู้ขอ B ส่งตาม
      When  เจ้าหน้าที่เปิดดูรายละเอียด และนักศึกษาเปิดดูรายละเอียดเดียวกัน
      Then  เจ้าหน้าที่เห็นคำขอ 2 รายการ ลำดับที่ 1 คือ A ลำดับที่ 2 คือ B พร้อมเวลาที่ส่งและชื่อผู้ขอ
            ส่วนนักศึกษาไม่เห็นรายการคำขอและชื่อผู้ขอใด ๆ
```

เหตุผล: DOM-REQ-01 ให้ส่งคำขอซ้อนกันได้ และผู้ที่ได้รับอนุมัติก่อนได้อุปกรณ์
เจ้าหน้าที่จึงต้องเห็นว่าใครส่งก่อนหลังตอนพิจารณา ทีมตัดสินให้แสดงที่หน้ารายละเอียดของ 001
ไม่แสดงบนหน้าจอของ 002 (FR-BRQ-05 ก) เพราะเจ้าหน้าที่ดูอุปกรณ์รายชิ้นจากหน้านี้อยู่แล้ว

## สัญญา API ระหว่าง 001 กับ 002 (ล็อกไว้ใน CR นี้ ต่างฝ่ายต่างทำได้ไม่ต้องรอกัน)

| | |
|---|---|
| endpoint | `GET /api/v1/equipment/items/{assetCode}/requests` (หลังบ้านรับที่ `/v1/...` เพราะ proxy ของ Vite ตัด `/api`) |
| เจ้าของ | **002** (plan 002 ข้อ 4, T-18 ของ 002) ลงทะเบียนที่ mux ชั้นนอกใน `backend/cmd/server/main.go` ครอบด้วย `auth.Middleware` |
| route | ไม่ชนกับ `/v1/equipment/` ของ 001 เพราะ Go 1.22 ขึ้นไปส่ง request ให้ pattern ที่เจาะจงกว่า ไม่ต้องแก้ `equipment/handler.go` |
| เฉพาะ | เจ้าหน้าที่ นักศึกษาได้ 403 รหัส `FORBIDDEN_ROLE` ตาม CON-TECH-03 (รหัสที่ 004 ลงทะเบียนไว้แล้ว ใช้กับกรณีบทบาทไม่มีสิทธิ์) |
| response 200 | `[{requestId, queuePosition, submittedAt, requesterName}]` เรียงตาม `queuePosition` (1 = ส่งก่อน) ไม่มีคำขอค้าง = `[]` |
| คำขอที่นับ | คำขอที่ "ค้างอยู่" ตามที่ 002 นิยามใน FR-BRQ-05 (ก) ถ้า 002 เปลี่ยนนิยาม ต้องแจ้ง 001 |
| error | ใช้รหัสและรูปแบบ `{code, message}` จาก CON-TECH-03 |
| ผู้เรียก | หน้ารายละเอียดของ 001 (`EquipmentDetail.jsx`) เรียก**ทุกครั้ง** ถ้าได้ 403 `FORBIDDEN_ROLE` ไม่แสดงส่วนนี้ หน้าจอไม่ต้องรู้บทบาทของผู้ใช้ |

ระหว่างที่ endpoint ของ 002 ยังไม่เสร็จ 001 เขียนหน้าจอและ test ด้วย client จำลองที่คืนรูปแบบข้างบน

## สิ่งที่ต้องแลก
- หน้ารายละเอียดของ 001 พึ่ง endpoint ของ 002 ถ้า 002 ล่ม ส่วนลำดับคำขอแสดงไม่ได้
  (ส่วนอื่นของหน้ารายละเอียดยังแสดงได้ ไม่ทำให้ทั้งหน้าพัง)
- ชื่อผู้ขอเป็นชื่อที่พิมพ์เอง อาจไม่ตรงกับชื่อจริงในระบบมหาวิทยาลัย เจ้าหน้าที่ต้องรู้ที่มานี้
