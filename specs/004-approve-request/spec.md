# Feature: อนุมัติคำขอยืมปกติ (Approve Request)
Spec ID: SPEC-APV-004 | Source: US-007, RQ-14, RQ-21, RQ-25 | Use case: UC-12
Owner: 660710758 นางสาวณัฐสุดา กัญญาบุญ (@natsuda05) | Status: Draft v1 | Updated: 2569-11-11
Backlog: BL-08 (specs/backlog.md) | SRS: docs/srs/SRS.md หัวข้อ 3.1.4

## Goal
เจ้าหน้าที่ตรวจสอบและอนุมัติหรือปฏิเสธคำขอยืมแบบปกติได้ในระบบก่อนส่งมอบอุปกรณ์ทุกครั้ง
และผู้ขอได้รับแจ้งผลทันทีที่มีการดำเนินการ (RQ-14, RQ-21)

## Scope
### In scope
- เจ้าหน้าที่ดูคำขอยืมแบบปกติที่สถานะ Requested แล้วอนุมัติหรือปฏิเสธ (UC-12, RQ-14)
- แจ้งผลการอนุมัติหรือปฏิเสธให้ผู้ขอผ่านระบบแจ้งเตือน Email (RQ-21, IF-NOT-01)
- ปฏิเสธคำขออื่นของอุปกรณ์รายชิ้นเดียวกันโดยอัตโนมัติเมื่อมีคำขอหนึ่งได้รับอนุมัติ (Q-SH-06 ส่วนที่ทีมตัดสินแล้ว)
- บันทึกประวัติการพิจารณาทุกครั้ง (RQ-25)
- เปลี่ยนสถานะของคำขอเท่านั้น สถานะอุปกรณ์ยังเป็น "ว่าง" (data-model.md ตาราง "ใครเปลี่ยนสถานะอุปกรณ์" แถว UC-12)
### Out of scope
- ส่งคำขอยืม UC-02 / UC-05 (002) และยกเลิกคำขอ UC-15 (003)
- คำขอยืมแบบค้างคืน: ตรวจเอกสาร UC-11 และบันทึกผลที่อาจารย์เซ็นนอกระบบ UC-14 (RQ-15, BL-17)
  รวมถึงสถานะ `approved_by_officer` และ `pending_advisor_approval` ใน data-model.md (ดู Q-APV-01)
- บันทึกการส่งมอบและกำหนดคืน UC-08 (005)
- นักศึกษาตรวจสอบสถานะคำขอของตนเอง UC-06 (RQ-10, BL-15)
- แสดงลำดับคำขอที่หน้ารายละเอียดอุปกรณ์ (001 ตาม Q-SH-05)
- จองอุปกรณ์ล่วงหน้า (BL-11, Won't ตาม N-01)
- แจ้งเตือนก่อนถึงกำหนดคืน (RQ-12)

- DOM-REQ-01 คำขอค้างของอุปกรณ์ชิ้นเดียวกันส่งซ้อนได้ คำขอที่ได้รับอนุมัติก่อนได้อุปกรณ์

## Requirements
ID ตรงกับ docs/srs/SRS.md หัวข้อ 3.1.4 (SRS ยังเป็น `[เติม]` ต้องเติมเมื่อ spec ผ่าน /clarify)

- FR-APV-01 ระบบต้องให้เจ้าหน้าที่ตรวจสอบและอนุมัติหรือปฏิเสธคำขอยืมแบบปกติ ก่อนส่งมอบอุปกรณ์ทุกครั้ง     <- RQ-14, US-007, UC-12
  (ก) อนุมัติแล้ว สถานะของคำขอเป็น `approved` / ปฏิเสธแล้ว เป็น `rejected` (data-model.md สถานะของคำขอยืม)
  (ข) สถานะอุปกรณ์ไม่เปลี่ยน (data-model.md แถว UC-12, CON-DATA-01)
  (ค) เมื่อคำขอหนึ่งได้รับอนุมัติ คำขออื่นที่ยังเป็น `requested` ของอุปกรณ์รายชิ้นเดียวกันถูกปฏิเสธอัตโนมัติ (Q-SH-06)
  (ง) ทุกการพิจารณาบันทึกประวัติ (RQ-25) ข้อมูลที่ต้องบันทึกรอ Q-APV-07
- FR-APV-02 ระบบต้องแจ้งผลการอนุมัติหรือปฏิเสธคำขอยืมแบบปกติให้ผู้ขอทราบทันทีที่มีการดำเนินการ ผ่านระบบแจ้งเตือน Email     <- RQ-21, IF-NOT-01
  คำว่า "ทันที" และเนื้อหาของ Email รอ Q-APV-02, Q-APV-03

## Acceptance Criteria
ID ของ AC ทุกข้อรอทีมอนุมัติ (Q-APV-10)
- AC-APV-01 (FR-APV-01, CON-DATA-01): Given เจ้าหน้าที่ผ่านการยืนยันตัวตนแล้ว และมีคำขอยืมแบบปกติสถานะ `requested` ของอุปกรณ์รายชิ้นที่สถานะ "ว่าง";
  When เจ้าหน้าที่อนุมัติคำขอนั้น;
  Then สถานะของคำขอเป็น `approved` และสถานะของอุปกรณ์รายชิ้นยังเป็น "ว่าง"
- AC-APV-02 (FR-APV-01): Given เจ้าหน้าที่ผ่านการยืนยันตัวตนแล้ว และมีคำขอยืมแบบปกติสถานะ `requested`;
  When เจ้าหน้าที่ปฏิเสธคำขอนั้น;
  Then สถานะของคำขอเป็น `rejected` และสถานะของอุปกรณ์รายชิ้นไม่เปลี่ยน
- AC-APV-03 (FR-APV-01, DOM-REQ-01): Given อุปกรณ์รายชิ้นเดียวกันมีคำขอ A และ B สถานะ `requested`;
  When เจ้าหน้าที่อนุมัติคำขอ A;
  Then คำขอ A เป็น `approved` และคำขอ B เป็น `rejected`
- AC-APV-04 (FR-APV-02, IF-NOT-01): Given เจ้าหน้าที่เพิ่งอนุมัติหรือปฏิเสธคำขอ;
  When ระบบบันทึกผลสำเร็จ;
  Then ระบบส่ง Email แจ้งผลถึงผู้ขอผ่าน IF-NOT-01 (เวลาและเนื้อหารอ Q-APV-02, Q-APV-03)
- AC-APV-05 (NFR-SEC-01, IF-IDP-01, CON-TECH-03): Given ผู้ใช้ที่ยังไม่ยืนยันตัวตน หรือมีบทบาทนักศึกษา;
  When เรียกการอนุมัติหรือปฏิเสธ;
  Then ระบบไม่ดำเนินการ ตอบ error ตาม CON-TECH-03 และสถานะของคำขอคงเดิม

## Assumptions & Open Questions
- ASM-01 ผู้ใช้ UC-12 คือบทบาทเจ้าหน้าที่เท่านั้น ตาม Use Case Diagram (constraints.md หัวข้อบทบาทในระบบ)
- ASM-02 ระหว่างรอ Q-SH-03 prototype ใช้ auth จำลอง (ทีมเลือกเอง ไม่ได้มาจาก spec)
- ASM-03 ข้อมูลคำขอมาจากตาราง `borrow_request` ของ 002 (migration 0003): ผู้ขอ (`requester_id`, `requester_name`, `student_code`),
  อุปกรณ์รายชิ้น, ประเภทการยืม, วัตถุประสงค์ 3 ค่า, ช่วงเวลาที่ต้องการยืม (`start_at`, `end_at`), เวลาที่ส่ง
  ตารางนี้ไม่มี Email ของผู้ขอ (ดู Q-APV-04)

คำถามร่วม (ดูรายละเอียดที่ constraints.md):
- Q-SH-03 auth service ใช้โปรโตคอลอะไร และส่งบทบาทกับภาควิชามาในรูปแบบใด
- Q-SH-06 (ส่วนที่ยังไม่ตอบ) ต้องแจ้งผู้ขอที่ถูกปฏิเสธตามไหม และเจ้าหน้าที่ต้องอนุมัติตามลำดับที่มาก่อนหรือข้ามได้ (ดู Q-APV-05, Q-APV-06)
- Q-SH-08 ถ้าระบบยืนยันตัวตนเชื่อมต่อไม่ได้ ระบบต้องทำอย่างไร

คำถามเฉพาะฟีเจอร์นี้:
- Q-APV-01 data-model.md เขียนว่า UC-12 (004) ตั้งสถานะ `approved_by_officer` ให้คำขอค้างคืน และ UC-14 (004) ตั้ง `approved` / `rejected`
  แต่ SRS 3.1.4 และ BL-08 ให้ 004 ทำเฉพาะยืมปกติ 004 ต้องรับคำขอค้างคืนด้วยไหม -> ทีม
- Q-APV-02 "ทันที" ใน RQ-21 คือภายในกี่วินาที และถ้าส่ง Email ไม่สำเร็จ ระบบต้องทำอย่างไร -> ทีม
- Q-APV-03 Email ผลอนุมัติและผลปฏิเสธต้องมีข้อมูลอะไร (หัวข้อ, ข้อความ, วันเวลารับ-คืน, สถานที่รับ) -> ทีม
- Q-APV-04 Email ของผู้ขอมาจากไหน: ระบบยืนยันตัวตนส่งมา, ประกอบจากรหัสนักศึกษา หรือให้ผู้ขอกรอก (002 ไม่มีคอลัมน์อีเมล) -> ทีม
- Q-APV-05 คำขอที่ถูกปฏิเสธอัตโนมัติเพราะมีคำขออื่นได้รับอนุมัติ ต้องแจ้งผู้ขอไหม และบันทึกผู้ดำเนินการเป็นใคร -> ทีม (Q-SH-06)
- Q-APV-06 เจ้าหน้าที่ต้องอนุมัติตามลำดับเวลาที่ส่งไหม หรือข้ามได้ ถ้าข้ามได้ต้องระบุเหตุผลไหม -> ทีม (Q-SH-06)
- Q-APV-07 ประวัติการพิจารณา (RQ-25) ต้องบันทึกอะไรบ้าง -> ทีม
- Q-APV-08 แดชบอร์ดของเจ้าหน้าที่แสดงคำขอใดบ้าง (เฉพาะวันนี้ เฉพาะภาควิชาตนเอง) เรียงอย่างไร และแสดงข้อมูลอะไร -> ทีม
- Q-APV-09 การปฏิเสธต้องระบุเหตุผลไหม และกรณีพิเศษ (คำขอถูกยกเลิกแล้ว, พิจารณาแล้ว, อุปกรณ์ไม่ "ว่าง", เจ้าหน้าที่ 2 คนกดพร้อมกัน,
  คำขอค้างจนเลยเวลาที่ผู้ขอต้องการยืม) ระบบต้องทำอย่างไร -> ทีม
- Q-APV-10 ทีมอนุมัติ ID ของ AC-APV-01 ถึง 05 ไหม -> ทีม
