กติกา: Constraint ที่ใช้มากกว่า 1 ฟีเจอร์ เขียนที่นี่ **ที่เดียว** spec ของแต่ละฟีเจอร์อ้าง ID ในหมวด Constraints ไม่ copy ข้อความ
ถ้าแก้ไฟล์นี้ ต้องทำ CR และดู Impact Analysis กับทุก spec ที่อ้าง ID นั้น (ดู rtm.md ของแต่ละฟีเจอร์)
`RQ-xx` = ข้อที่ xx ในตาราง Requirement บน Miro (ดู docs/srs/SRS.md หัวข้อ 3.1)

## เทคโนโลยี (CON-TECH)
- CON-TECH-01 ใช้ฐานข้อมูล PostgreSQL ตาม Infrastructure ที่กำหนดไว้
- CON-TECH-02 ให้บริการผ่าน HTTPS เท่านั้น deploy ด้วย Docker บน on-campus server หรือ cloud VM
- CON-TECH-03 ทุก endpoint ตอบ error ด้วย body `{"code": "<รหัส>", "message": "<ข้อความภาษาไทยสำหรับผู้ใช้>"}`
  โดยใช้รหัสจากรายการกลางด้านล่าง หน้าจอตัดสินใจจากรหัส ไม่ใช่จากข้อความ (CR-004 2569-11-11)

  | รหัส | HTTP | ความหมาย | ใครใช้แล้ว |
  |---|---|---|---|
  | `UNAUTHENTICATED` | 401 | ไม่มี session หรือหมดอายุ | 001, 002, 003, 004, 006 |
  | `PRINCIPAL_INCOMPLETE` | 403 | ยืนยันตัวตนได้ แต่ไม่มีภาควิชาหรือบทบาทไม่รู้จัก | 001, 002 |
  | `FORBIDDEN_DEPARTMENT` | 403 | เข้าถึงอุปกรณ์ของภาควิชาอื่น ต้องไม่ส่งข้อมูลอุปกรณ์กลับ | 001, 002, 004, 006 (อุปกรณ์หรือการยืมของภาควิชาอื่น) |
  | `UPSTREAM_UNAVAILABLE` | 503 | ฐานข้อมูลหรือระบบภายนอกไม่ตอบ | 001, 002, 003, 004, 006 |
  | `VALIDATION_FAILED` | 422 | ข้อมูลที่ส่งมาไม่ครบหรือผิดกติกา แนบรายชื่อช่องที่ผิด | 002, 003 (`fields: ["reason"]` CR-006), 004 |
  | `ITEM_NOT_AVAILABLE` | 409 | อุปกรณ์ไม่ได้อยู่ในสถานะ "ว่าง" แล้ว | 002, 004 |
  | `REQUEST_NOT_APPROVED` | 409 | คำขอยืมไม่อยู่ในสถานะที่ทำสิ่งนี้ได้ (ยังไม่อนุมัติ หรือส่งมอบไปแล้ว) | 005 (ลงทะเบียน 2569-11-11) |
  | `BORROWER_MISMATCH` | 409 | ผู้ที่ยืนยันตัวตนไม่ใช่ผู้ส่งคำขอ | 005 (ลงทะเบียน 2569-11-11) |
  | `DUPLICATE_REQUEST` | 409 | ผู้ขอคนเดิมมีคำขอที่ยังไม่จบของอุปกรณ์ชิ้นเดิมอยู่แล้ว | 002 |
  | `HAS_OVERDUE_LOAN` | 409 | ผู้ขอมีอุปกรณ์ที่คืนเกินกำหนดค้างอยู่ | 002 |
  | `FORBIDDEN_ROLE` | 403 | ยืนยันตัวตนได้และบทบาทรู้จัก แต่บทบาทนี้ไม่มีสิทธิ์ทำรายการนี้ (เช่น นักศึกษาเรียกการอนุมัติ) | 001, 002 (เปิดไฟล์แนบของคำขอผู้อื่น T-15 ดู CR-007), 004, 005, 003 (เจ้าหน้าที่เรียกหน้าคำขอของนักศึกษาหรือสั่งยกเลิก CR-006), 006 (นักศึกษาเรียกหน้ารับคืน) |
  | `REQUEST_CANCELLED` | 409 | คำขอถูกผู้ขอยกเลิกแล้ว (`cancelled`) จึงพิจารณาไม่ได้ | 004 |
  | `REQUEST_ALREADY_DECIDED` | 409 | คำขอได้รับการพิจารณาไปแล้วก่อนที่หน้าจอของผู้เรียกจะโหลด | 004 |
  | `REQUEST_DECIDED_CONCURRENTLY` | 409 | คำขอเพิ่งถูกพิจารณาโดยผู้อื่นหลังหน้าจอของผู้เรียกโหลด (กดพร้อมกัน) | 004 |
  | `NOT_FIRST_IN_QUEUE` | 409 | ไม่ใช่คำขอที่ส่งก่อนสุดที่ยังรออนุมัติของอุปกรณ์ชิ้นนั้น | 004 |
  | `APPROVAL_CUTOFF_PASSED` | 409 | เลยเวลาที่อนุมัติได้แล้ว (16:00 น. ของวันที่เริ่มยืม) | 004 |
  | `REQUEST_NOT_FOUND` | 404 | ไม่มีคำขอยืมรหัสนี้ เป็นคำขอที่ฟีเจอร์นั้นไม่ได้รับผิดชอบ หรือคำขอนั้นไม่มีสิ่งที่ขอ (เช่น ไม่มีไฟล์แนบ) ตอบเหมือนกันหมดเพื่อไม่บอกว่าเลขคำขอใดมีอยู่จริง (DOM-PRIV-01) | 004 (ลงทะเบียน 2569-11-12), 002 (ไฟล์แนบของคำขอ T-15 ดู CR-007), 003 (คำขอของผู้อื่นตอบเหมือนไม่มี CR-006) |
  | `ALREADY_APPROVED` | 409 | ยกเลิกคำขอไม่ได้ เพราะคำขอได้รับการอนุมัติแล้ว แนบ `status` ของคำขอ (ต่างจาก `REQUEST_ALREADY_DECIDED` ของ 004 ที่ใช้ตอนเจ้าหน้าที่พิจารณาคำขอซึ่งพิจารณาไปแล้ว ทั้ง approved และ rejected) | 003 (ลงทะเบียน 2569-11-12 CR-006) |
  | `NOT_CANCELLABLE` | 409 | ยกเลิกคำขอไม่ได้ เพราะสถานะเป็น rejected, handed_over, returned หรือ cancelled แนบ `status` ของคำขอ | 003 (ลงทะเบียน 2569-11-12 CR-006) |
  | `ITEM_NOT_FOUND` | 404 | ไม่มีอุปกรณ์รหัสครุภัณฑ์นี้ หรือรหัสรุ่นไม่ถูกต้อง (เรื่องของอุปกรณ์ ไม่ใช่คำขอยืม ซึ่งใช้ `REQUEST_NOT_FOUND`) | 001 (ลงทะเบียน 2569-11-12) |
  | `METHOD_NOT_ALLOWED` | 405 | เรียก endpoint ด้วย method ที่ไม่รองรับ (เช่น POST ไปที่ endpoint ที่มีแค่ GET) แนบ header `Allow` ตามเดิม | ทุกฟีเจอร์ ผ่านตัวครอบใน `platform` (001 ลงทะเบียน 2569-11-12) |
  | `NO_OPEN_LOAN` | 409 | อุปกรณ์รหัสครุภัณฑ์นี้ไม่มีการยืมที่ยังไม่คืน (ไม่มีรหัสนี้ ไม่ได้อยู่ในสถานะ "ถูกยืม" หรือคืนไปแล้ว รวมกรณีบันทึกคืนพร้อมกัน) จึงบันทึกการรับคืนไม่ได้ | 006 (ลงทะเบียน 2569-11-12) |
  | `CONDITION_REQUIRED` | 422 | ไม่ได้ระบุสภาพตอนรับคืน หรือสภาพไม่ใช่ ปกติ / ชำรุด | 006 (ลงทะเบียน 2569-11-12) |
  | `LOAN_NOT_FOUND` | 404 | ไม่มีการยืมรหัสนี้ (เรื่องของการยืม ไม่ใช่คำขอยืม ซึ่งใช้ `REQUEST_NOT_FOUND` หรืออุปกรณ์ ซึ่งใช้ `ITEM_NOT_FOUND`) | 006 (ลงทะเบียน 2569-11-12) |

  ฟีเจอร์ที่ต้องการรหัสใหม่ ให้เพิ่มแถวในตารางนี้ก่อนใช้ ห้ามตั้งรหัสเองในโค้ดโดยไม่ลงทะเบียน

## ข้อมูล (CON-DATA)
- CON-DATA-01 สถานะอุปกรณ์มีค่าที่เป็นไปได้ 3 ค่าเท่านั้น: ว่าง, ถูกยืม, ไม่พร้อมใช้งาน (RQ-09, CR-002)
- CON-DATA-03 อุปกรณ์แต่ละชิ้นมีรหัสครุภัณฑ์ไม่ซ้ำกัน แม้เป็นรุ่นเดียวกัน

## กฎของโดเมน (DOM)
- DOM-PRIV-01 นักศึกษาเห็นได้เฉพาะสถานะ และกำหนดคืนหรือป้าย "เลยกำหนดคืน" (FR-EQS-04)
  ไม่เห็นชื่อผู้ยืมรายอื่น
- DOM-AUDIT-01 บันทึก audit log ทุกครั้งที่เข้าถึงข้อมูลอุปกรณ์ (ผู้เข้าถึง, เวลา, เงื่อนไขที่ค้น)
- DOM-ACCESS-01 นักศึกษาเข้าดูรายการอุปกรณ์ได้เฉพาะภาควิชาของตนเอง (ปิด Q-03 ของ 001)
  นักศึกษาภาควิชาอื่นไม่เห็นรายการและรายละเอียดอุปกรณ์
- DOM-LOAN-01 การยืมแบบปกติต้องคืนภายในเวลา 16:00 น. ของวันเดียวกับที่ยืม และใช้งานอุปกรณ์ได้เฉพาะภายในพื้นที่มหาวิทยาลัย
  ไม่ใช้กับการยืมแบบค้างคืน (RQ-17, CR-002)

- DOM-REQ-01 อุปกรณ์ที่มีคำขอยืมค้าง (ยังไม่อนุมัติ หรืออนุมัติแล้วแต่ยังไม่ส่งมอบ) ยังมีสถานะ "ว่าง"
  นักศึกษาคนอื่นส่งคำขออุปกรณ์ชิ้นเดียวกันซ้อนได้ คำขอที่ได้รับอนุมัติก่อนได้อุปกรณ์
  ระบบต้องแสดงเวลาที่ส่งและลำดับของคำขอที่มาก่อน (ปิด Q-SH-01 ทีมตัดสิน 2569-11-09)
  ใครเห็นลำดับ และเห็นชื่อผู้ขอหรือไม่ รอ Q-SH-05 / คำขออื่นหลังมีคนได้รับอนุมัติ รอ Q-SH-06

## การเชื่อมต่อระบบภายนอก (IF)
- IF-IDP-01 ต้องได้รับผลยืนยันตัวตนจากระบบยืนยันตัวตนของมหาวิทยาลัย (Auth API, RQ-23) ก่อนเข้าถึงข้อมูล
  และต้องได้รับข้อมูลภาควิชาของผู้ใช้กลับมาเพื่อใช้ตรวจ DOM-ACCESS-01
- IF-NOT-01 ส่งการแจ้งเตือนถึงผู้ใช้ผ่านระบบแจ้งเตือน Email (Architecture บน Miro, RQ-12, RQ-21)

## บทบาทในระบบ (จาก Use Case Diagram)
- ผู้ใช้ระบบมี 2 บทบาท: นักศึกษา, เจ้าหน้าที่
- อาจารย์หัวหน้าโครงการ **ไม่ใช้ระบบโดยตรง** อนุมัติการยืมค้างคืนด้วยการเซ็นเอกสารนอกระบบ แล้วเจ้าหน้าที่บันทึกผล (RQ-15, UC-11, UC-14)

## คำถามที่กระทบหลายฟีเจอร์ (ยังไม่มีคำตอบ ห้ามเดา)
- Q-SH-01 [ปิดแล้ว 2569-11-09 ทีมตัดสิน ยังไม่ได้ยืนยันกับนักคอมพิวเตอร์] ยังเป็น "ว่าง" ส่งซ้อนได้ ใครอนุมัติก่อนได้ไป
  ต้องแสดงเวลาและลำดับของคนที่ขอมาก่อน -> DOM-REQ-01
- Q-SH-02 [ปิดแล้ว 2569-11-02 CR-002] ยืมปกติ: เจ้าหน้าที่อนุมัติ (RQ-14, UC-12) / ค้างคืน: อาจารย์เซ็นนอกระบบ เจ้าหน้าที่บันทึกผล (RQ-15, UC-14)
- Q-SH-03 auth service ใช้โปรโตคอลอะไร และส่ง role + ภาควิชามาในรูปแบบใด (เดิมคือ Q-P1 ใน plan ของ 001)
  -> ถามนักเทคโนโลยีสารสนเทศ ระหว่างรอ prototype ใช้ auth จำลอง (ทีมเลือกเอง ไม่ได้มาจาก spec)
  **ตอบ 2569-11-13 (เจ้าของ 004 แจ้งในแชตของ 004):** prototype ใช้ auth จำลองตลอด ไม่ต่อระบบจริง (004 บันทึกเป็น ASM-02 และปิด T-39)
- Q-SH-04 [ปิดแล้ว 2569-11-11 ทีมตัดสิน] กำหนดคืนของการยืมค้างคืน = 16:00 น. ของวันที่สิ้นสุดการยืมที่ผู้ขอระบุ
  (DOM-LOAN-01 ยังใช้กับยืมปกติเท่านั้น) เขียนไว้ที่ FR-BRQ-10 (ค) ของ 002 และ DM-05
  กระทบ: 001 (ป้ายเลยกำหนดคืน), 005 (บันทึกกำหนดคืนตอนส่งมอบ)
- Q-SH-05 [ปิดแล้ว 2569-11-11 ทีมตัดสิน] (จาก DOM-REQ-01) ลำดับและเวลาของคำขอที่มาก่อน
  แสดง**เฉพาะเจ้าหน้าที่** ที่**หน้ารายละเอียดอุปกรณ์ของ 001** และเจ้าหน้าที่เห็นชื่อผู้ขอรายอื่นได้
  (ไม่ขัด DOM-PRIV-01 เพราะนักศึกษายังไม่เห็นชื่อผู้อื่น)
  001 เพิ่ม FR-EQS-11 และ AC-EQS-17 แล้ว (CR-005 อนุมัติ 2569-11-12) ส่วน 002 เป็นผู้บันทึกเวลาที่ส่งให้
  ผ่าน `GET /api/v1/equipment/items/{assetCode}/requests` นักศึกษาได้ 403 `FORBIDDEN_ROLE` (สัญญา API ใน specs/changes/CR-005.md)
  กระทบ: 001 (FR-EQS-11), 002 (FR-BRQ-05), 004
- Q-SH-06 [ปิดแล้ว 2569-11-12 ทีมตัดสิน (ส่วนแรก 2569-11-11)] (จาก DOM-REQ-01) เมื่อคำขอหนึ่งได้รับอนุมัติแล้ว

  คำตอบส่วนที่เหลือ: **ต้องแจ้งผู้ขอที่ถูกปฏิเสธ** ตาม RQ-21 (Q-SH-06 ใน spec ของ 002, FR-APV-01 (จ) ของ 004)
  และ**อนุมัติตามลำดับเวลาที่ส่งเท่านั้น ข้ามไม่ได้** (ASM-04 ของ 004 ทีมตัดสิน 2569-11-11)
  (ไฟล์นี้อัปเดตตาม spec ของ 002 และ 004 เมื่อ 2569-11-13) กระทบ: 002, 003, 004, 005

- Q-SH-07 (RQ-27) บทลงโทษเมื่อนักศึกษาไม่คืนตามกำหนดคืออะไร (เช่น งดยืมกี่วัน), ใครเป็นผู้กำหนด และใครบันทึกในระบบ?
