## Goal
นักศึกษาที่ยืนยันตัวตนแล้ว ส่งคำขอยืมอุปกรณ์ที่ว่างได้ด้วยตนเองจากหน้าอุปกรณ์ โดยไม่ต้องเขียนเอกสารด้วยมือ
และระบบตรวจความพร้อมของอุปกรณ์กับสิทธิ์ของผู้ขอให้ก่อนสร้างคำขอ ทำให้คำขอทุกรายการมีผู้ขอและเวลาที่ส่งซึ่งตรวจสอบย้อนหลังได้

## Scope
### In scope
- ส่งคำขอยืมอุปกรณ์ที่สถานะ "ว่าง" พร้อมตรวจสถานะซ้ำทั้งตอนเปิดฟอร์มและตอนกดส่ง
- แบบฟอร์มคำขอ: ประเภทการยืม (ปกติ / ค้างคืน), วัตถุประสงค์, ช่วงเวลาที่ต้องการยืม และการตรวจความครบถ้วนก่อนส่ง
- การยืมแบบค้างคืน (UC-05): ระบุเหตุผลและแนบเอกสารประกอบ (ใบบันทึกข้อความ) ตาม RQ-16
- ปฏิเสธคำขอใหม่อัตโนมัติเมื่อผู้ขอมีอุปกรณ์คืนเกินกำหนดค้างอยู่ (RQ-20)
- รองรับคำขอซ้อนบนอุปกรณ์ชิ้นเดียวกัน และเปิดเผยเวลาที่ส่งกับลำดับผ่าน API ให้ 001 นำไปแสดง (DOM-REQ-01, CR-003)
- จำกัดการส่งคำขอเฉพาะอุปกรณ์ของภาควิชาผู้ขอ (DOM-ACCESS-01)
- บันทึก audit log ของการส่งคำขอ ทั้งกรณีสำเร็จและถูกปฏิเสธ (DOM-AUDIT-01, RQ-25)
### Out of scope
- อนุมัติหรือปฏิเสธคำขอ และแจ้งผลให้ผู้ขอ (UC-12, RQ-14, RQ-21 -> 004)
- ตรวจเอกสารขออนุมัติค้างคืนและบันทึกผลที่อาจารย์เซ็นนอกระบบ (UC-11, UC-14, RQ-15 -> BL-17, 004)
  ฟีเจอร์นี้ครอบคลุมเฉพาะการ**ส่ง**คำขอค้างคืนเท่านั้น
- ยกเลิกคำขอยืม (UC-15, RQ-03 -> 003) | ตรวจสอบสถานะคำขอของตนเอง (UC-06, RQ-10 -> BL-15)
- บันทึกการส่งมอบและกำหนดคืน (UC-08, RQ-17 -> 005) | บันทึกการรับคืน (UC-09 -> 006)
- เปลี่ยนสถานะอุปกรณ์ (ฟีเจอร์นี้ไม่เปลี่ยนสถานะใด ๆ ดูตาราง "ใครเปลี่ยนสถานะอุปกรณ์" ใน specs/000-shared/data-model.md)
- แสดงลำดับและเวลาของคำขอที่มาก่อนบนหน้าจอ (เป็นงานของ 001 หน้ารายละเอียดอุปกรณ์ CR-003)
- แปลงวันที่สิ้นสุดการยืมเป็นกำหนดคืน และบันทึกกำหนดคืน (เป็นงานของ 005 ตอนส่งมอบ CR-003)
- ยืนยันตัวตน (IF-IDP-01) ถือว่าทำสำเร็จแล้วก่อนเข้าฟีเจอร์นี้ (precondition ของ UC-02)

## Constraints
ใช้ร่วม (ข้อความเต็มอยู่ที่ specs/000-shared/constraints.md ห้าม copy มาไว้ที่นี่):
- CON-TECH-01 ฐานข้อมูล PostgreSQL
- CON-TECH-02 HTTPS เท่านั้น deploy ด้วย Docker
- CON-TECH-03 รูปแบบ error `{code, message}` และรหัสจากรายการกลาง (เพิ่มโดย CR-004)
- CON-DATA-01 สถานะอุปกรณ์ 3 ค่าเท่านั้น (ฟีเจอร์นี้ส่งคำขอได้เฉพาะชิ้นที่สถานะ "ว่าง")
- CON-DATA-03 รหัสครุภัณฑ์ไม่ซ้ำกัน (ใช้ระบุอุปกรณ์ที่ขอยืม)
- DOM-PRIV-01 นักศึกษาไม่เห็นชื่อผู้ยืมหรือผู้ขอรายอื่น (กระทบการแสดงลำดับคำขอใน FR-BRQ-05)
- DOM-AUDIT-01 audit log ทุกครั้งที่เข้าถึงข้อมูลอุปกรณ์
  (ใช้กับการอ่านสถานะอุปกรณ์ตอนเปิดฟอร์มและตอนกดส่ง ส่วน log ของการส่งคำขอใช้ RQ-25 ดู FR-BRQ-08 และ CR-003)
- DOM-ACCESS-01 นักศึกษาเข้าถึงได้เฉพาะอุปกรณ์ภาควิชาของตนเอง
- DOM-LOAN-01 ยืมแบบปกติคืนภายใน 16:00 น. วันเดียวกัน และใช้งานในพื้นที่มหาวิทยาลัย (ไม่ใช้กับค้างคืน)
- DOM-REQ-01 อุปกรณ์ที่มีคำขอยืมค้างยังมีสถานะ "ว่าง" ส่งซ้อนได้ ต้องแสดงเวลาและลำดับของคำขอที่มาก่อน
- IF-IDP-01 ต้องยืนยันตัวตนผ่านระบบของมหาวิทยาลัยก่อน และได้ภาควิชาของผู้ใช้กลับมา
เฉพาะฟีเจอร์นี้:
- ยังไม่มี Constraint เฉพาะฟีเจอร์นี้ ข้อตกลงทางเทคนิคกับ 001 (เลข migration และชนิดของ id) อยู่ที่ ASM-BRQ-03
  เพราะเป็นข้อตกลงระหว่างทีม ไม่ใช่ข้อกำหนดจากผู้ใช้

## Requirements
ID ตรงกับ docs/srs/SRS.md หัวข้อ 3.1.2 ทุกข้อ ห้ามเปลี่ยนเลข

- FR-BRQ-01 ระบบต้องให้ผู้ขอส่งคำขอยืมอุปกรณ์รายชิ้นที่สถานะ "ว่าง" โดยรับรหัสครุภัณฑ์จาก FR-EQS-06
  และต้องตรวจสถานะอุปกรณ์ซ้ำทั้งตอนเปิดฟอร์มและตอนกดส่ง
  ถ้าสถานะไม่ใช่ "ว่าง" แล้ว ต้องไม่สร้างคำขอ และแจ้งสถานะล่าสุด     <- US-002, FR-EQS-06, UC-02 main flow 1-2, exception 2a
- FR-BRQ-02 แบบฟอร์มคำขอต้องให้ผู้ขอระบุวัตถุประสงค์การยืมแบบ**แยกประเภท** โดยเลือก 1 ค่าจาก 3 ตัวเลือก
  (ทีมตัดสิน 2569-11-11): **เพื่อการเรียน / เพื่อทำกิจกรรม / อื่น ๆ**
  (ก) ถ้าเลือก "อื่น ๆ" ต้องพิมพ์ระบุเพิ่มในช่องข้อความ จึงจะส่งคำขอได้
  (ข) ถ้าเลือก 2 ค่าแรก ไม่ต้องพิมพ์อะไรเพิ่ม
  ใช้ช่องเดียวกันทั้งการยืมปกติและค้างคืน และเก็บทั้งค่าที่เลือกกับข้อความที่พิมพ์ไว้กับคำขอ
                                                                   <- RQ-18, RQ-16, UC-02 main flow 5, DM-06
- FR-BRQ-03 ระบบต้องตรวจความครบถ้วนของข้อมูลในฟอร์มก่อนอนุญาตให้ส่ง ถ้าไม่ครบ ต้องไม่สร้างคำขอ
  และระบุช่องที่ยังขาด ช่องที่ต้องครบ 5 ช่อง (ทีมตัดสิน 2569-11-11):
  ชื่อ-นามสกุล, รหัสนักศึกษา, วันและเวลาที่เริ่มยืม, วันและเวลาที่คืน, วัตถุประสงค์การยืม (FR-BRQ-02)
  (ก) ชื่อ-นามสกุลและรหัสนักศึกษา **ผู้ขอพิมพ์เอง** ระบบไม่เติมให้ (ดู ASM-BRQ-06 เรื่องผู้ขอที่บันทึกจริง)
  (ข) ช่วงเวลาระบุเป็นวันที่และเวลาเริ่มถึงสิ้นสุด ใช้กับการยืมทั้งแบบปกติและค้างคืน
  (ค) ถ้าเป็นการยืมแบบปกติ และเวลาสิ้นสุดเกิน 16:00 น. ของวันเดียวกับที่เริ่มยืม
      ระบบต้อง**ปฏิเสธไม่ให้ส่ง** และแจ้งว่าการยืมแบบปกติต้องคืนภายใน 16:00 น. ของวันเดียวกัน (DOM-LOAN-01)
                                                                   <- RQ-22, DOM-LOAN-01, CR-003, UC-02 main flow 6 และ 9, exception 9a
- FR-BRQ-04 เมื่อส่งสำเร็จ ระบบต้องสร้างคำขอยืมด้วยสถานะเริ่มต้น "รออนุมัติ" (ค่าในฐานข้อมูลคือ `requested`
  ตามตาราง "สถานะของคำขอยืม" ใน specs/000-shared/data-model.md)
  พร้อมบันทึกผู้ขอ (รหัสผู้ใช้จาก IF-IDP-01 ไม่ใช่รหัสนักศึกษาที่พิมพ์ในฟอร์ม ดู ASM-BRQ-06)
  อุปกรณ์รายชิ้น ประเภทการยืม และเวลาที่ส่ง (Asia/Bangkok)
  และต้องไม่เปลี่ยนสถานะอุปกรณ์ ฟีเจอร์นี้ตั้งสถานะของคำขอได้เพียงค่าเดียวคือ `requested`
                                                                   <- UC-02 postcondition, main flow 10, DM-06, DOM-REQ-01
- FR-BRQ-05 ระบบต้องอนุญาตให้ส่งคำขอซ้อนกับคำขอที่ค้างอยู่ของ**ผู้อื่น**บนอุปกรณ์ชิ้นเดียวกัน
  และบันทึกเวลาที่ส่งเพื่อใช้เรียงลำดับคำขอที่มาก่อน
  (ก) ฟีเจอร์นี้ต้อง**เปิดเผยเวลาที่ส่งและลำดับของคำขอที่ค้างอยู่ของอุปกรณ์ชิ้นนั้นผ่าน API**
      ให้ 001 เรียกไปแสดง ไม่แสดงเองบนหน้าจอของ 002 (ทีมตัดสิน 2569-11-11, CR-003)
      การแสดงผลเป็นหน้าที่ของ 001 หน้ารายละเอียดอุปกรณ์ เห็นเฉพาะเจ้าหน้าที่ ซึ่งเห็นชื่อผู้ขอรายอื่นได้
      (ปิด Q-SH-05 กระทบ 001 ต้องเพิ่ม FR ผ่าน CR ตามที่ spec 001 เขียนไว้)
  (ข) ถ้าผู้ขอ**คนเดิม**ส่งคำขออุปกรณ์ชิ้นเดิมซ้ำขณะที่คำขอเก่ายัง**ไม่จบ**
      คือสถานะเป็น `requested`, `approved_by_officer`, `pending_advisor_approval` หรือ `approved`
      ระบบต้องปฏิเสธและไม่สร้างคำขอใหม่ (ปิด Q-BRQ-04 / ขยายขอบเขตโดย CR-004 2569-11-11)
                                                                   <- DOM-REQ-01, Q-SH-05, Q-BRQ-04
- FR-BRQ-06 ระบบต้องปฏิเสธคำขอใหม่โดยอัตโนมัติเมื่อผู้ขอมีอุปกรณ์ที่คืนเกินกำหนดค้างอยู่ในระบบ
  พร้อมแจ้งเหตุผล และไม่สร้างคำขอ นิยามที่ทีมตัดสิน 2569-11-11:
  (ก) ถือว่าเกินกำหนดทันทีเมื่อเลยเวลา 16:00 น. ของกำหนดคืน
  (ข) เมื่อคืนอุปกรณ์แล้ว ผู้ขอกลับมาส่งคำขอได้เมื่อถึง **00:00 น. ของวันถัดไป** ตามเขตเวลา Asia/Bangkok
      (ไม่ใช่ทันทีที่คืน และไม่ใช่ครบ 24 ชั่วโมง) ทีมตัดสิน 2569-11-11
  (ค) นับเฉพาะอุปกรณ์ของ**ภาควิชาตนเอง** ไม่นับของค้างในภาควิชาอื่น (ทีมตัดสิน 2569-11-11, DOM-ACCESS-01)
  (ง) ข้อนี้อยู่ใน prototype รอบนี้ ส่วนบทลงโทษอื่นตาม RQ-27 ไม่อยู่ในขอบเขต (Q-SH-07 ยังไม่มีนิยาม)
                                                                   <- RQ-20, BL-23 (เฉพาะส่วน RQ-20), UC-02 precondition 3, main flow 3, exception 3a
- FR-BRQ-07 ระบบต้องอนุญาตให้นักศึกษาส่งคำขอได้เฉพาะอุปกรณ์ของภาควิชาตนเอง
  คำขอข้ามภาควิชาต้องถูกปฏิเสธ และผู้ขอต้องไม่ได้รับข้อมูลอุปกรณ์      <- DOM-ACCESS-01, FR-EQS-10
- FR-BRQ-08 ระบบต้องบันทึก audit log ทุกครั้งที่มีการส่งคำขอ ทั้งกรณีสำเร็จและถูกปฏิเสธ
  ระบุผู้ขอ เวลา รหัสครุภัณฑ์ และผลลัพธ์
  (ที่มาคือ RQ-25 อย่างเดียว ตัดการอ้าง DOM-AUDIT-01 ออกเพราะข้อความของมันครอบคลุมเฉพาะ
  การเข้าถึงข้อมูลอุปกรณ์ ทีมตัดสิน 2569-11-11, CR-003)              <- RQ-25, UC-02 main flow 11, DM-07
- FR-BRQ-09 เมื่อบันทึกคำขอไม่สำเร็จหลังกดส่ง (ระบบหรือฐานข้อมูลขัดข้อง) ระบบต้องแจ้งข้อผิดพลาดแก่ผู้ขอ
  ไม่สร้างคำขอค้างไว้ และการส่งใหม่ต้องไม่ทำให้เกิดคำขอซ้ำซ้อนของรายการเดียวกัน
  ก่อนกด "ส่งคำขอยืม" ผู้ขอต้องกลับไปแก้ไขข้อมูลในฟอร์มได้โดยระบบยังไม่สร้างคำขอ
                                                                   <- UC-02 exception 10a, alternative 8a
- FR-BRQ-10 ระบบต้องรองรับการยืมแบบค้างคืนในฟีเจอร์นี้ โดยผู้ขอเลือกประเภทการยืม "ปกติ" หรือ "ค้างคืน"
  (ก) เลือก "ค้างคืน" ต้องเลือกวัตถุประสงค์การยืม (FR-BRQ-02) และแนบไฟล์ใบบันทึกข้อความ
      **ตั้งแต่ตอนส่งคำขอ** จึงจะส่งได้ ไฟล์ที่รับคือ PDF หรือรูปถ่าย ขนาดไม่เกิน **10MB**
      เก็บเป็นไฟล์บนเครื่องที่รันระบบ และเปิดดูได้เฉพาะเจ้าหน้าที่กับเจ้าของคำขอ
      (ทีมตัดสิน 2569-11-11 ดู ASM-BRQ-07 เรื่องที่เก็บไฟล์)
      "ระบุเหตุผลการยืม" ตาม RQ-16 ใช้ช่องวัตถุประสงค์ของ FR-BRQ-02 ช่องเดียวกัน
      ถ้าเลือก "อื่น ๆ" ก็พิมพ์ระบุในช่องเดียวกันนั้น ไม่มีช่องเหตุผลแยกสำหรับค้างคืน
  (ข) เลือก "ปกติ" ระบบต้องแสดงเงื่อนไขการยืมปกติก่อนส่ง

## Acceptance Criteria
- [ ] AC-BRQ-01 (FR-BRQ-01)
      Given นักศึกษาเปิดแบบฟอร์มคำขอของอุปกรณ์ชิ้นที่สถานะ "ว่าง"
      When  อุปกรณ์ชิ้นนั้นถูกเปลี่ยนเป็น "ถูกยืม" ระหว่างกรอก แล้วนักศึกษากดส่งคำขอ
      Then  ระบบต้องไม่สร้างคำขอ และแจ้งสถานะล่าสุดของอุปกรณ์
- [ ] AC-BRQ-02 (FR-BRQ-02)
      Given นักศึกษาเปิดแบบฟอร์มคำขอของอุปกรณ์ที่ว่าง
      When  เลือกวัตถุประสงค์ "เพื่อการเรียน" กรอกข้อมูลครบ แล้วส่งคำขอสำเร็จ
      Then  คำขอที่บันทึกต้องมีวัตถุประสงค์ตรงกับค่าที่เลือก
      และ
      Given ยังไม่ได้เลือกวัตถุประสงค์การยืม
      When  กดส่งคำขอ
      Then  ระบบต้องไม่สร้างคำขอ และระบุว่าต้องเลือกวัตถุประสงค์
- [ ] AC-BRQ-14 (FR-BRQ-02 ก)
      Given นักศึกษาเลือกวัตถุประสงค์ "อื่น ๆ"
      When  ไม่พิมพ์ข้อความระบุ แล้วกดส่งคำขอ
      Then  ระบบต้องไม่สร้างคำขอ และระบุว่าต้องพิมพ์ระบุวัตถุประสงค์
      และ
      Given เลือก "อื่น ๆ" แล้วพิมพ์ข้อความระบุ
      When  ส่งคำขอสำเร็จ
      Then  คำขอที่บันทึกต้องเก็บทั้งค่า "อื่น ๆ" และข้อความที่พิมพ์
- [ ] AC-BRQ-03 (FR-BRQ-03)
      Given ข้อมูลคำขอไม่ครบถ้วน (เช่น ไม่ได้ระบุวันและเวลาที่คืน)
      When  นักศึกษากดส่งคำขอ
      Then  ระบบต้องไม่สร้างคำขอ และระบุช่องข้อมูลที่ยังต้องกรอก
            (ช่องที่ตรวจ 5 ช่อง: ชื่อ-นามสกุล, รหัสนักศึกษา, วันและเวลาที่เริ่มยืม, วันและเวลาที่คืน, วัตถุประสงค์การยืม)
- [ ] AC-BRQ-13 (FR-BRQ-03 ค)
      Given นักศึกษาเลือกประเภทการยืมเป็น "ปกติ" และระบุเวลาเริ่มยืมวันนี้ 09:00 น.
      When  ระบุเวลาคืนเป็น 18:00 น. ของวันเดียวกัน แล้วกดส่งคำขอ
      Then  ระบบต้องปฏิเสธไม่ให้ส่ง ไม่สร้างคำขอ
            และแจ้งว่าการยืมแบบปกติต้องคืนภายใน 16:00 น. ของวันเดียวกัน
- [ ] AC-BRQ-04 (FR-BRQ-04)
      Given นักศึกษาไม่มีรายการคืนเกินกำหนดค้างอยู่ และอุปกรณ์ชิ้นนั้นสถานะ "ว่าง"
      When  กรอกข้อมูลครบถ้วนและกดส่งคำขอ
      Then  ระบบต้องสร้างคำขอด้วยสถานะ "รออนุมัติ" พร้อมผู้ขอ อุปกรณ์รายชิ้น ประเภทการยืม
            และเวลาที่ส่งตามเวลา Asia/Bangkok โดยสถานะของอุปกรณ์ยังเป็น "ว่าง"
- [ ] AC-BRQ-05 (FR-BRQ-05 ก)
      Given อุปกรณ์ชิ้นหนึ่งมีคำขอค้างอยู่แล้ว 1 คำขอจากนักศึกษาคนอื่น
      When  นักศึกษาอีกคนส่งคำขอของอุปกรณ์ชิ้นเดียวกัน
      Then  ระบบต้องรับคำขอไว้ และเมื่อเรียกข้อมูลลำดับของอุปกรณ์ชิ้นนั้นผ่าน API
            ต้องได้คำขอเดิมเป็นลำดับที่ 1 และคำขอใหม่เป็นลำดับที่ 2 เรียงตามเวลาที่ส่ง
            โดยหน้าจอของ 002 ไม่แสดงข้อมูลคำขอของผู้อื่นให้นักศึกษาเห็น
- [ ] AC-BRQ-11 (FR-BRQ-05 ข)
      Given นักศึกษาคนหนึ่งมีคำขอของอุปกรณ์ชิ้นหนึ่งอยู่แล้ว ไม่ว่าสถานะจะเป็น `requested` หรือ `approved`
      When  ส่งคำขอของอุปกรณ์ชิ้นเดิมซ้ำอีกครั้ง
      Then  ระบบต้องปฏิเสธ ไม่สร้างคำขอใหม่ และแจ้งว่ามีคำขอของอุปกรณ์ชิ้นนี้ค้างอยู่แล้ว
      และ
      Given คำขอเดิมถูกยกเลิกหรือถูกปฏิเสธไปแล้ว
      When  ส่งคำขอของอุปกรณ์ชิ้นเดิมใหม่
      Then  ระบบต้องรับคำขอได้ตามปกติ
- [ ] AC-BRQ-06 (FR-BRQ-06)
      Given นักศึกษามีอุปกรณ์ที่ยังไม่คืน และเลยเวลา 16:00 น. ของกำหนดคืนไปแล้ว
      When  พยายามส่งคำขอยืมใหม่
      Then  ระบบต้องปฏิเสธคำขอ แจ้งสาเหตุ และไม่สร้างคำขอ
- [ ] AC-BRQ-12 (FR-BRQ-06 ข)
      Given นักศึกษาคืนอุปกรณ์ที่เกินกำหนดแล้วเมื่อเวลา 14:00 น. ของวันนี้
      When  ส่งคำขอยืมใหม่เวลา 23:59 น. ของวันเดียวกัน แล้วส่งอีกครั้งเวลา 00:01 น. ของวันถัดไป
            (เทียบด้วยเขตเวลา Asia/Bangkok)
      Then  คำขอเวลา 23:59 น. ต้องถูกปฏิเสธ ส่วนคำขอเวลา 00:01 น. ต้องส่งได้
- [ ] AC-BRQ-07 (FR-BRQ-07)
      Given นักศึกษาสังกัดภาควิชาที่ 2 และอุปกรณ์ชิ้นเป้าหมายเป็นของภาควิชาที่ 1
      When  ส่งคำขอยืมอุปกรณ์ชิ้นนั้น
      Then  ระบบต้องปฏิเสธ ไม่สร้างคำขอ และไม่ส่งข้อมูลอุปกรณ์กลับไป
- [ ] AC-BRQ-08 (FR-BRQ-08)
      Given มีผู้ขอที่ส่งคำขอสำเร็จ 1 ครั้ง และถูกปฏิเสธ 1 ครั้ง
      When  ตรวจ audit log
      Then  ต้องมีบันทึกครบทั้ง 2 ครั้ง ระบุผู้ขอ เวลา รหัสครุภัณฑ์ และผลลัพธ์ของแต่ละครั้ง
- [ ] AC-BRQ-09 (FR-BRQ-09)
      Given การบันทึกคำขอลงฐานข้อมูลไม่สำเร็จ
      When  นักศึกษากดส่งคำขอ แล้วกดส่งใหม่อีกครั้งจนสำเร็จ
      Then  ครั้งแรกต้องแจ้งข้อผิดพลาดและไม่มีคำขอค้างในระบบ และเมื่อสำเร็จต้องมีคำขอเพียง 1 รายการ
- [ ] AC-BRQ-10 (FR-BRQ-10)
      Given นักศึกษาเลือกประเภทการยืมเป็น "ค้างคืน"
      When  ยังไม่เลือกวัตถุประสงค์ หรือยังไม่แนบไฟล์ใบบันทึกข้อความ แล้วกดส่งคำขอ
      Then  ระบบต้องไม่สร้างคำขอ และระบุสิ่งที่ยังขาด
      และ
      Given แนบไฟล์ที่ไม่ใช่ PDF หรือรูปถ่าย หรือไฟล์ขนาดเกิน 10MB
      When  กดส่งคำขอ
      Then  ระบบต้องไม่สร้างคำขอ และแจ้งชนิดกับขนาดไฟล์ที่รับได้
      และ
      Given นักศึกษาเลือกประเภทการยืมเป็น "ปกติ"
      When  อยู่ในแบบฟอร์มคำขอก่อนกดส่ง
      Then  ระบบต้องแสดงเงื่อนไขว่าต้องคืนภายใน 16:00 น. ของวันเดียวกัน และใช้งานภายในพื้นที่มหาวิทยาลัย

## Assumptions & Open Questions
คำถามของฟีเจอร์นี้ใช้รหัส Q-BRQ-xx เพื่อไม่ให้ชนกับ Q-xx ของ 001 ส่วน Q-SH-xx คือคำถามของกลาง

- ASM-BRQ-01 ผู้ขอยืนยันตัวตนสำเร็จแล้ว และระบบรู้บทบาทกับภาควิชาของผู้ขอก่อนเข้าฟีเจอร์นี้ (IF-IDP-01, DM-08)
- ASM-BRQ-02 [ยืนยันแล้ว 2569-11-11] หน่วยที่ขอยืมคือ "อุปกรณ์รายชิ้น" ตาม FR-EQS-06
  ทีมยืนยันคำตอบของ Q-16 ว่าเป็นรายชิ้น ตาราง `borrow_request` จึงอ้างอุปกรณ์รายชิ้น
  (เจ้าของ 001 ต้องปิด Q-16 ใน spec ของตนด้วย)
- ASM-BRQ-03 ข้อตกลงทางเทคนิคกับเจ้าของ 001 (ไม่ใช่ข้อกำหนดจากผู้ใช้ รายละเอียดอยู่ใน plan.md)
  ใช้เลข migration `0003_borrow_request.up.sql` ตามตารางเลข migration ใน specs/000-shared/data-model.md
  คอลัมน์ id ของ `borrow_request` เป็น SERIAL (INT) ให้ชนิดตรงกับ `audit_log.request_id` ที่เป็น INT
  และ 002 เป็นผู้เพิ่ม foreign key จาก `audit_log.request_id` มาที่ `borrow_request.id` ใน migration ของตนเอง
  migration เดียวกันนี้ต้องเพิ่มค่า `request` เข้าไปใน CHECK ของคอลัมน์ `audit_log.action` ด้วย (Q-BRQ-07)
  โดยไม่แก้ไฟล์ `0002_audit_log.up.sql` ตามกติกาที่เขียนไว้ในไฟล์นั้น
- ASM-BRQ-04 [ยืนยันแล้ว 2569-11-11] เอกสารประกอบการยืมค้างคืนเป็นไฟล์ที่ผู้ขออัปโหลดเข้าระบบ
  ตั้งแต่ตอนส่งคำขอ ไม่ใช่เอกสารกระดาษที่ส่งนอกระบบ (RQ-16)
- ASM-BRQ-05 [ยกเลิก 2569-11-11 ทีมทบทวนแล้วกลับไปใช้ตัวเลือกประเภท] เดิมเขียนว่าเป็นช่องพิมพ์อิสระ
  ซึ่งขัดกับ RQ-18 ทีมจึงเปลี่ยนเป็น**เลือกจากรายการตัวเลือก** ตาม RQ-18 เดิม
  **ไม่ต้องแก้ RQ-18 บน Miro แล้ว** ID นี้เก็บไว้เพื่อการตามรอย ห้ามนำกลับมาใช้กับเรื่องอื่น
- ASM-BRQ-06 [ทีมตัดสิน 2569-11-11 ไม่ได้ถามผู้ใช้] ชื่อ-นามสกุลและรหัสนักศึกษาที่ผู้ขอพิมพ์
  เป็นข้อมูลประกอบคำขอ ส่วน "ผู้ขอ" ที่ระบบใช้ตรวจสิทธิ์ (DOM-ACCESS-01) บันทึกใน audit log
  และใช้อ้างอิงย้อนหลัง ยังเป็นรหัสผู้ใช้จาก IF-IDP-01 เสมอ
  เพราะถ้าใช้ค่าที่พิมพ์เอง จะสวมชื่อผู้อื่นได้และตรวจภาควิชาไม่ได้
  **ทีมยืนยันแล้ว 2569-11-11: ยึดรหัสจากการล็อกอินเป็นเจ้าของคำขอเสมอ**
- ASM-BRQ-07 [ทีมตัดสิน 2569-11-11 ไม่ได้ถามผู้ใช้] ไฟล์แนบเก็บเป็นไฟล์บนเครื่องที่รันระบบ
  ไม่ได้เก็บในฐานข้อมูล และเปิดดูได้เฉพาะเจ้าหน้าที่กับเจ้าของคำขอ
  **ยังไม่มี CON หรือ IF ข้อไหนใน 000-shared รองรับเรื่องที่เก็บไฟล์** ถ้าทีมต้องการให้เป็นข้อผูกมัด
  ต้องเพิ่ม Constraint ใหม่ผ่าน CR
- Q-BRQ-01 [ปิดแล้ว 2569-11-11 CR-003] วัตถุประสงค์การยืมเลือกจากรายการตัวเลือก 1 ค่า
  (ทีมตอบ "พิมพ์เอง" 2 รอบ แล้วทบทวนกลับมาใช้ตัวเลือกเมื่อเห็นว่าขัด RQ-18)
  แก้ FR-BRQ-02 แล้ว รายการตัวเลือกจริงรอ Q-BRQ-16
- Q-BRQ-02 [ปิดแล้ว 2569-11-11 ทีมตัดสิน] ช่องที่ต้องครบคือ ชื่อ-นามสกุล, รหัสนักศึกษา,
  วันและเวลาที่เริ่มยืม, วันและเวลาที่คืน, เหตุผลที่ยืม และช่วงเวลาระบุเป็นวันที่+เวลาเริ่มถึงสิ้นสุด
  ใช้กับการยืมทั้งแบบปกติและค้างคืน (เขียนลง FR-BRQ-03 แล้ว ส่วนที่ยังค้างแยกเป็น Q-BRQ-11 และ Q-BRQ-12)
- Q-BRQ-03 [ปิดแล้ว 2569-11-11 ทีมตัดสิน] FR-BRQ-06 "มีอุปกรณ์ที่คืนเกินกำหนดค้างอยู่"

  นับเฉพาะอุปกรณ์ของภาควิชาตนเอง / ทำการปฏิเสธอัตโนมัติใน prototype รอบนี้
  เขียนลง FR-BRQ-06 และ AC-BRQ-12 แล้ว
  บันทึกไว้เพื่อการตามรอย — ตอนตัดสินมีเอกสารขัดกันอยู่ดังนี้
